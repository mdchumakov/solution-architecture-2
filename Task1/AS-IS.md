# AS-IS: диагностика текущей архитектуры

## 1. Основание и границы анализа

Источники фактов — [контекст](../docs/context.md) и [исходная схема](task.md). Исходного кода, трассировок и профилей БД нет, поэтому ниже отдельно обозначены факты, архитектурные выводы и гипотезы для проверки.

AdScale — гибридный монолит на C++, Go, Python и Node.js в одном production-кластере. Все домены используют один экземпляр PostgreSQL. Нет кеша, очередей, контейнеризации и read-replica; деплой выполняется вручную. Названия `Service` на исходной схеме обозначают части монолита, а не доказанно независимые сервисы. Метки `JDBC` трактуются как доступ к PostgreSQL: конкретные драйверы для разных языков не установлены.

## 2. Компоненты и потоки

| Участок | Поток и ответственность | Зависимость |
| --- | --- | --- |
| Приём ставки | DSP → Ad Server → Auction Engine | Ad Server читает таргетинг, Auction Engine — ставки и кампании из общей БД |
| Результат аукциона | Auction Engine → Delivery Service | Подготовка HTML/JS; на исходной схеме входит в последовательную цепочку |
| Показ и клик | Пользователь ↔ Delivery Service → Statistics Service → PostgreSQL | Каждое событие приводит к прямой записи без буфера |
| Управление рекламой | Рекламодатель → Advertiser Dashboard → PostgreSQL | CRUD кампаний конкурирует с аукционами и статистикой |
| Финансы | Dashboard → Financial Service → PostgreSQL | Балансы, списания и счета зависят от той же БД |
| Пополнение | Dashboard → внешний платёжный шлюз | Подтверждение платежа и обработка повторов на схеме не раскрыты |
| Отчётность | Dashboard → Analytics Service → PostgreSQL | Тяжёлые запросы используют ресурсы production-БД |

Направление OpenRTB сохраняется согласно условию: внешний DSP присылает запрос и получает ответ. Обратный синхронный вызов партнёра во время расчёта ставки не предполагается. Исходная схема не показывает точный момент отправки bid-response и не доказывает, что ответ ждёт записи статистики. Это требуется проверить трассировкой; сами показы и клики происходят позже аукциона.

## 3. Узкие места и риски

Приоритет **P0** — риск нарушения SLA или финансовой корректности; **P1** — ограничение роста и управляемости.

| ID | Наблюдаемый факт | Следствие / риск | Приоритет и направление устранения |
| --- | --- | --- | --- |
| R1 | Ad Server и Auction Engine синхронно читают PostgreSQL | Ожидание соединения, сети и SQL входит в время ответа; рост числа копий монолита увеличит нагрузку на БД | P0: подготовленная модель чтения и независимое масштабирование Bidding Service |
| R2 | Один экземпляр PostgreSQL для всех доменов | Отказ экземпляра останавливает основные функции; конкуренция за CPU, I/O, память, WAL и соединения | P0: HA, разделение нагрузки, затем владение БД по доменам |
| R3 | Statistics Service пишет события напрямую | Всплеск показов/кликов повышает задержки транзакций и аукционов; нет средства сгладить пик | P0: долговечный журнал событий и пакетная обработка |
| R4 | Аналитика работает на production-БД | Сканирования и сортировки конкурируют с OLTP; длинные транзакции могут мешать очистке старых версий | P0: отдельная OLAP-проекция, временно выделенная реплика |
| R5 | Монолит объединяет разные профили нагрузки | Нельзя избирательно добавить мощности только расчёту ставки или обработке событий; ошибки и релизы затрагивают общие ресурсы | P1: границы модулей и постепенное выделение сервисов |
| R6 | Ручные выкладки, нет контейнеризации | Неодинаковые окружения, риск ошибки, медленный откат; фактическая частота инцидентов неизвестна | P1: воспроизводимые сборки, автоматические проверки и canary |
| R7 | Один production-кластер | Инцидент площадки затрагивает всю систему; топология узлов и резервное копирование не описаны | P0: проверка восстановления, затем резервирование по зонам и регионам |
| R8 | Нет запаса производительности и документированных контрактов | Новая интеграция может усилить каскадные отказы; таймауты, повторы и финансовая идемпотентность неизвестны | P0: измерения, ограничение нагрузки, явные контракты |

Тяжёлый `SELECT` сам по себе не означает блокировку всех записей: PostgreSQL использует MVCC. Проблема здесь прежде всего в совместном потреблении ресурсов; конкретные блокировки нужно подтвердить через ожидания и длительные транзакции. [PostgreSQL: MVCC](https://www.postgresql.org/docs/current/mvcc-intro.html).

## 4. Влияние на время отклика и масштабирование

Из условия: пик **15 000 RPS**, **P95 110–120 мс** при требовании **≤ 100 мс**. Нарушение уже составляет 10–20 мс. Интеграция добавит 20%: `15 000 × 1,2 = 18 000 RPS`. При отсутствии запаса увеличение числа запросов повышает ожидание ресурсов; нельзя обоснованно считать, что latency вырастет ровно на 20%.

Для одного запроса критический путь можно представить так:

```text
Tответа = Tсети + Tочереди + TAdServer + Tчтения_таргетинга
        + TAuction + Tчтения_кампаний + Tформирования_ответа
        + Tдополнительных_синхронных_вызовов
```

Это декомпозиция времени одного запроса, а не формула сложения P95 отдельных этапов. Вклад каждого этапа без трассировок неизвестен. Указанные в контексте задержки свыше 150 мс — сценарий риска, а не результат проведённого теста.

Добавление копий монолита не устраняет общий предел PostgreSQL. Read-replica способна разгрузить чтение, но не ускоряет запись событий и добавляет задержку репликации. Вертикальное увеличение БД даёт временный резерв, сохраняя общий домен отказа. Извлечение одного Auction Engine без удаления его SQL-зависимости также не решает проблему.

## 5. Что измерить до миграции

1. Сквозную latency по партнёрам и этапам: P50/P95/P99, deadline miss, ошибки, долю инфраструктурных no-bid, время ожидания пулов.
2. CPU и очереди Ad Server/Auction Engine; частоту и длительность SQL, I/O/WAL, блокировки, активные соединения и стоимость отчётов.
3. События в секунду отдельно от bid RPS, размер сообщения, долю выигранных аукционов и распределение нагрузки по кампаниям.
4. Корректность повторных платежных уведомлений, потерянных событий и восстановления БД из резервной копии.
5. Поведение на 15 000 и 18 000 RPS с параллельной аналитикой; результаты станут базой сравнения canary.

Диагноз определяет порядок изменений: сначала измеримость и защита общей БД, затем выделение критического контура и событий, после — разделение остальных доменов. Соответствие рисков требованиям и решениям приведено в [Drivers.md](Drivers.md).
