# ADR-002. Приоритет выделения сервиса ставок

- **Дата:** 2026-09-28.
- **Статус:** принято в рамках проектного решения.
- **Драйверы:** F1–F2, F4, Q1–Q4, Q7.

## Контекст

Ad Server и Auction Engine читают общую БД в критическом пути. Партнёр требует ответ за 80 мс, тогда как текущий P95 уже 110–120 мс. Простое извлечение Auction Engine оставит SQL-зависимость и добавит сетевую задержку. Контур ставок должен масштабироваться независимо, сохраняя правила работы с бюджетом.

## Решение

Первым доменным сервисом выделить **Bidding Service**, объединяющий подбор кандидатов Ad Server и аукцион Auction Engine. Переиспользовать алгоритмы C++, интеграционный код писать с учётом существующего опыта Go. RTB Gateway отдельно отвечает за адаптеры DSP и deadline; Delivery обслуживает показ после аукциона.

Ставка вычисляется по локальной версионированной модели в RAM. Redis служит её восстанавливаемым кешем, Campaign/временный Legacy Adapter предоставляют снимки, события обновляют модель в фоне. Промах не приводит к SQL-запросу. Непрогретые экземпляры исключаются из балансировки, просроченные данные — из аукциона.

Finance заранее выдаёт непересекающиеся квоты, обеспеченные резервом денег. Bidding расходует квоту локально, а окончательный учёт выполняет Finance по идемпотентным событиям. После перезапуска старая квота не переиспользуется автоматически. Redis-копия баланса не является основанием для расхода. Механизм и ограничения описаны в [TO-BE](../TO-BE.md#43-защита-бюджета-без-удалённого-вызова-на-каждую-ставку).

Приоритет Bidding не означает, что он вводится без подготовительных работ: сбор метрик, HA, поток событий и разгрузка аналитики начинаются раньше или параллельно.

## Альтернативы

- **Начать с кабинета:** проще выделить, но влияние на критический путь мало.
- **Начать только со статистики:** разгружает запись, но сохраняет синхронное чтение общей БД на ставке; используется как параллельная мера.
- **Извлечь только Auction Engine:** создаёт распределённую цепочку с прежним узким местом.
- **Начать с Finance:** полезная граница, но перенос наиболее чувствительных данных повышает риск трёхмесячного этапа; сначала изолируется финансовый интерфейс внутри монолита.

## Последствия

Появляется возможность отдельно масштабировать CPU и исключить OLTP из запроса ставки. Цена — память для проекций, контроль свежести, прогрев и сложность квот. Сбой или задержка обновлений снижает участие в аукционах; это наблюдаемая деградация, а не успешное выполнение SLA за счёт no-bid.

## Проверка и пересмотр

Shadow должен подтвердить сопоставимость бизнес-решений, нагрузочные тесты — критерии Q1/Q2, а crash/replay-тесты — Q4. Проверяется горячая кампания и маленький бюджет, а не только равномерная нагрузка. Если безопасные квоты или доставка расчётных уведомлений не подтверждены, запуск не выполняется; отдельно пересматривается финансовый протокол, а не отключается проверка бюджета.
