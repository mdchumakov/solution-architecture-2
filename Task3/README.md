## Этапы

К третьему месяцу нужен общий поток не менее 18 000 bid RPS. Campaign и Finance ещё работают в монолите: им выделяем схемы и роли в существующем PostgreSQL, вводим outbox и интерфейсы владельцев. Bidding, Event Collector и Analytics работают отдельно. PostgreSQL получает standby, Kafka — три брокера, ClickHouse — один шард с двумя репликами. Redis обслуживает только фоновые операции Bidding. Перед закупкой нужно проверить стоимость этой топологии и доступность независимых доменов отказа.

К году Campaign и Finance получают собственные БД и независимые ресурсы. RTB обслуживается в двух регионах, а финансовая запись остаётся у одного владельца для каждого счёта. Цель — 50 000 bid RPS и доступность 99,9%. Число шардов определяется нагрузкой каждого хранилища: частота событий и размер набора кампаний в условии не заданы.

Требования задержки сохраняются: новому DSP нужен ответ в пределах 80 мс на его стороне, существующему трафику — P95 ≤ 100 мс. Репликация и резервное копирование не включаются в путь ставки; Bidding использует локальную модель и обеспеченную квоту. Все RPO/RTO и размеры в этих документах — проектные цели для испытаний, а не измеренные результаты.

## Проверка решения

| Сценарий | Критерий |
| --- | --- |
| Разные роли БД и Kafka ACL | Ни один сервис не записывает таблицы или topics чужого владельца; аналитика не читает production-primary |
| 18 000 RPS и отдельно поток событий с горячей кампанией | Соблюдены бюджеты Task2, измерены lag, IO, CPU и запас; рост lag не скрывается средними значениями |
| Failover PostgreSQL во время выдачи квоты | Старый писатель отключён, подтверждённые транзакции сохранены, повтор команды не создаёт второй grant |
| Сброс Redis и одновременный запуск Bidding | Источники защищены ограничением прогрева, холодные процессы не готовы к трафику, устаревшие модели исключаются |
| Дубли событий, crash после SQL commit, replay за 7 суток | Нет повторных проводок и увеличения аналитических сумм из-за дублей |
| Потеря брокера или реплики ClickHouse | Подтверждённые данные доступны в принятой модели отказов; нагрузка не превосходит возможности оставшихся узлов |
| Восстановление из резервной копии на пустой инфраструктуре | Измерены реальный RPO/RTO, проверены ключи, схемы, счета, версии кампаний и контрольные суммы |
| Потеря региона к годовому этапу | Старый Finance fenced; новая выдача квот заблокирована до сверки; известен пробел асинхронной репликации |

DevOps отвечает за репликацию, копии и восстановление инфраструктуры. Владельцы сервисов проверяют данные после восстановления; Finance отдельно подтверждает возможность снова выдавать квоты. Полный прогон восстановления проводим до подключения DSP и затем ежемесячно для PostgreSQL, ежеквартально для регионального сценария. В отчёте об учениях фиксируем объём данных, длительность, потерянный интервал и нерешённые расхождения.
