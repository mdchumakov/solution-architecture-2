# Масштабирование хранилищ

## PostgreSQL: запись и реплики

Для Campaign и Finance выбираем primary/standby (master-slave в формулировке задания). Primary принимает команды, одна синхронная standby в другом доступном домене отказа подтверждает WAL. Финансовые транзакции используют `synchronous_commit=on` и явно настроенный синхронный standby: без настройки списка standby это значение не обеспечивает синхронную репликацию.

Если standby недоступна, финансовая запись приостанавливается. Автоматически переключать её в асинхронный режим ради доступности нельзя: тогда исчезнет обещанный RPO=0 при потере primary. Failover выполняется только после изоляции старого писателя и проверки подтверждённого WAL. Координатор HA требует кворума на трёх независимых узлах или эквивалентной гарантии управляемой услуги. У двух серверов БД без арбитража нет безопасного автоматического решения при сетевом разделении.

Это следует из модели [streaming и synchronous replication PostgreSQL](https://www.postgresql.org/docs/18/warm-standby.html): асинхронная реплика может отставать, синхронный commit ждёт выбранную standby. Нужные параметры и поведение при отказе проверяем на выбранной версии, а не считаем следствием наличия двух VM.

| Чтение | Куда направляем |
| --- | --- |
| Проверка денег, выдача квоты, изменение кампании | Только primary владельца |
| Ответ сразу после изменения | Результат команды или чтение primary, чтобы не показать старую версию |
| Списки кампаний, исторические счета без требования немедленной свежести | Асинхронная read replica при допустимом lag; при превышении лимита показываем задержку или ограничиваем запрос |
| Снимки Bidding | Replica только с известным watermark и подходящим снимком; иначе отдельный ограниченный пул primary |
| Тяжёлые отчёты по показам/кликам | ClickHouse, не primary PostgreSQL |

В первые недели read replica PostgreSQL временно разгружает старую аналитику. После перехода отчётов в ClickHouse она не является постоянным аналитическим хранилищем. Длинные запросы на standby могут мешать replay и удержанию WAL, поэтому у них отдельные ограничения времени и числа соединений. Реплики увеличивают доступность и мощность чтения, но не пропускную способность записи primary.

## Партиции и шарды

| Данные | Ключ и этап | Ограничения |
| --- | --- | --- |
| Campaign | Сначала одна БД, индексы `(advertiser_id, status)` и `(campaign_id, version)`. При подтверждённом пределе — виртуальные шарды по `advertiser_id` | Все кампании рекламодателя остаются вместе; крупный рекламодатель может получить выделенный шард |
| Finance | В первые три месяца без шардирования. При необходимости к году — владелец счёта по `advertiser_id`, все валютные счета и кампании рекламодателя на одном шарде | Баланс, grants и проводки операции остаются в одной транзакции. Переводы между владельцами требуют отдельного протокола; общий баланс из eventual-consistent сумм не используется |
| Финансовый ledger | Месячные партиции по времени записи проводки; контроль уникальности расчётов — отдельная таблица settlement/inbox без ограничения месяцем | Партиционирование упрощает архив, но не распределяет запись между серверами. ID дубля не может стать «новым» после смены месяца |
| Kafka | Партиции по campaign/grant согласно контракту topic | Число активных consumers в группе ограничено числом партиций; порядок только в пределах партиции |
| Analytics | Один шард × две реплики на старте; затем виртуальные бакеты `hash(campaign_id, event_id)` | Один и тот же event ID всегда попадает на тот же шард. Горячая кампания распределяется по событиям; отчёт по ней объединяет результаты шардов |
| ClickHouse внутри шарда | Месячная партиция по неизменяемому `occurred_at`; сортировка по `(campaign_id, event_type, occurred_at, event_id)` | Partition key управляет хранением, sorting key — чтением и дедупликацией; это разные задачи |
| Redis | Сначала primary + replica; Redis Cluster при превышении доступной памяти/потока прогрева | Ключи кампаний распределяются по hash slots. Независимые кампании не получают общий hash tag, создающий горячий слот |

Фиксированное число физических шардов не зашиваем в `hash(key) % N`: при добавлении узла такой алгоритм переместит большинство ключей и нарушит маршрутизацию повторов. Используем стабильные виртуальные бакеты и версионированную карту их размещения. Для Analytics запись и replay одной исторической эпохи используют ту же карту до завершения переноса.

Перенос бакета проходит через снимок, догон изменений и сверку. На переключении старый владелец перестаёт принимать новые записи; новый начинает после fencing и фиксации новой эпохи маршрута. До сверки запросы не суммируют одновременно старую и новую копии. Для Finance такой перенос выполняется с паузой команд владельца, а не с двумя активными writers.

## Analytics и read replicas

Выбираем self-managed ClickHouse с семейством ReplicatedMergeTree и ClickHouse Keeper: одна группа из трёх Keeper и две реплики каждого шарда в разных доменах отказа. Если доступна управляемая услуга, требования к её репликации проверяются отдельно. Consumer пишет в таблицу фактов с `insert_quorum=2`; при недоступной второй реплике Kafka хранит backlog, offset не продвигается после неподтверждённого insert.

ClickHouse отдельно реплицирует таблицы и распределяет данные между шардами; эти механизмы описаны в [документации ReplicatedMergeTree](https://clickhouse.com/docs/reference/engines/table-engines/mergetree-family/replication). Реплики одного шарда хранят один набор данных, запрос не должен суммировать обе копии. Distributed-запрос выбирает одну реплику каждого шарда. DDL и справочники также разворачиваются на всех нужных узлах.

Analytics не нужна дополнительная PostgreSQL read replica. Для роста чтения используем реплики ClickHouse, отдельные пулы запросов, предагрегации и ограничения на тяжёлые выгрузки. Свежесть контролируется watermark загрузки и lag выбранной реплики. При потере реплики чтение переключается на оставшуюся, а приём новых фактов может ждать восстановления кворума; UI показывает последнее подтверждённое время данных.

Если consumer повторил insert после потерянного ack, ClickHouse может временно содержать дубликаты. `ReplacingMergeTree` удаляет их при слияниях, поэтому фоновое слияние не считается достаточной гарантией корректного отчёта. Канонический запрос применяет `FINAL` либо явную группировку по устойчивому ключу с выбором версии. Периодические агрегаты пересчитываются из этого набора с заменой затронутого периода. Materialized view, которая просто суммирует каждый входящий insert, здесь не используется. Ограничения eventual-дедупликации описаны в [руководстве ClickHouse](https://clickhouse.com/docs/concepts/features/operations/update/replacing-merge-tree).

Для одного event ID поля ключа сортировки, время события и номер бакета неизменны. Исправление исходного события оформляется отдельным correction-событием со ссылкой на него. Иначе две версии окажутся в разных партициях или ключах и `ReplacingMergeTree` их не объединит. Полноту финансового отчёта подтверждает сверка с ledger Finance, а не время последнего insert.

## CQRS

Команды Campaign пишут PostgreSQL и outbox. Запрос ставки читает RAM-проекцию Bidding, отчёт читает ClickHouse. Это CQRS: модели записи и чтения имеют разные структуры и обновляются с задержкой. PostgreSQL остаётся источником текущего состояния Campaign и Finance; полного event sourcing всех доменов не вводим.

Лаг проекций виден отдельно от доступности API. После остановки кампании Bidding может использовать предыдущую версию в пределах согласованных 30 с. Если требуется мгновенная блокировка, придётся менять контракт и путь распространения; уменьшение TTL само по себе не докажет нулевую задержку.

## Два региона к году

RTB получает локальные RAM-проекции и независимые обеспеченные grants в каждом регионе. Finance имеет один home region для счёта; межрегиональное RPC не входит в bid-response. Региональные Kafka-кластеры реплицируют журнал асинхронно, сохраняя исходные event ID и регион источника. Префиксы/направления репликации исключают циклы. Kafka offset после переноса не считается тем же бизнес-идентификатором.

PostgreSQL DR standby в другом регионе получает WAL асинхронно. Перед её promotion старый писатель изолируется, сверяются не дошедшие операции и открытые grants. При разделении сети второй регион не начинает независимо выдавать деньги по старому снимку. Существующие квоты продолжают ограничивать ставки; неполная история может остановить новые квоты дольше, чем запуск самой БД. Ограничения RPO/RTO приведены в [reliability.md](reliability.md).

## Как выбрать мощность

Известны bid RPS, но неизвестны размер кампаний, события на запрос и длительность хранения. До закупки измеряем поток событий, средний и P99 размер payload, write/read throughput, долю горячих ключей и время replay.

Для Kafka нижняя оценка хранения: `E × S × T × RF`, где E — events/s, S — размер сохранённого события, T — retention в секундах. Например, при условных 5 000 events/s, 1 KiB и 7 сутках это около 3,1 TB логических данных и 9,3 TB при RF=3 до сжатия, индексов и резерва. Это пример расчёта, а не измеренный профиль AdScale.

Число партиций должно покрывать пиковую запись, скорость обработки consumers и требуемое время replay с запасом 30%. Аналогично измеряем WAL/IOPS PostgreSQL и скорость insert/merge/query ClickHouse. Для проекций учитываем две RAM-копии во время атомарной замены, индексы, кеш решений и runtime процесса. Минимальный резерв мощности проверяется при потере одного узла; обычная загрузка 70% сама по себе этого не гарантирует.
