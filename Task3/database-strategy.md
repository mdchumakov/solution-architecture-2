# Стратегия хранения данных

## Database per Service

Database per Service означает единственного владельца записи и доступ через его API или события. Отдельный экземпляр СУБД нужен для изоляции нагрузки и отказов. Collector, например, сохраняет события в Kafka и своей PostgreSQL не требует.

| Сервис | Хранилище и модель | Обоснование |
| --- | --- | --- |
| Bidding | RAM с неизменяемыми проекциями; собственный Redis как кеш прогрева | Запрос ставки не ждёт сети и SQL. Модель восстанавливается из Campaign и потока изменений. Расходуемые остатки grant не восстанавливаются из Redis |
| Campaign | PostgreSQL: кампании, правила, статусы, ссылки на креативы, версии и outbox | Нужны транзакции настроек и ограничений, уникальность и индексы для кабинета. Частота команд ниже bid RPS |
| Статистика / Event Collector | Kafka: журнал показов, кликов и уведомлений; долговечный архив в объектном хранилище | Collector проверяет и сохраняет факты, а не выполняет OLTP-запись на каждый клик. История и replay доступны нескольким потребителям |
| Analytics | ClickHouse: факты событий и производные агрегаты | Колоночное хранение и пакетная загрузка подходят для отчётов по большим временным диапазонам. Суммы расходов сверяются с Finance |
| Finance | PostgreSQL: счета, grants, settlement, проводки, inbox/idempotency, outbox | Атомарное резервирование денег, уникальность расчётного факта и согласованное обновление баланса |

Сервис статистики из задания соответствует Event Collector из Task1/Task2. Kafka topics принадлежат этому сервису, но брокеры образуют общую инфраструктуру с отдельными ACL и квотами. Analytics не становится владельцем финансовых фактов. Delivery хранит файлы креативов в объектном хранилище; Campaign хранит их ID и метаданные, а не бинарные файлы.

Через три месяца Campaign и Finance остаются в отдельных схемах монолита с разными ролями записи. Ограничиваем SQL-доступ модулей, запрещаем новые междоменные JOIN и общие таблицы для новых данных. На этом этапе изоляция ещё неполная: модули разделяют ресурсы и отказную область PostgreSQL. Через год каждому домену выделяется отдельная БД; сначала они могут находиться на общем HA-кластере, но Finance затем получает независимые диски, пул соединений и отказную область.

## Модели и ограничения

| Домен | Основные сущности и ключи |
| --- | --- |
| Campaign | `campaign(campaign_id PK, advertiser_id, version, status, currency, max_cpm_micros)`, `targeting_rule`, `creative_ref`, `outbox(event_id PK, aggregate_id, version, payload)` |
| Bidding | `CampaignProjection(campaign_id, version, checkpoint, fresh_until)`, `CreativeProjection`, локальный `BudgetGrant` и `LocalReservation`; детали — в [Task2](../Task2/bidding-service.md#модель-данных) |
| Finance | `account(account_id PK, advertiser_id, currency)`, `budget_grant(grant_id PK, instance_epoch, limit_micros)`, `settlement`, `ledger_entry`, `inbox`, `idempotency`, `outbox` |
| Collector | Конверт событий с устойчивым `event_id` и временем источника/приёма; схемы и ключи — в [event-streaming.md](event-streaming.md) |
| Analytics | `raw_events`, канонический набор уникальных событий, дневные/часовые агрегаты по кампании, площадке и типу события; checkpoint загрузки и watermark свежести |

В Finance деньги храним в целых микродолях одной валюты. Не складываем разные валюты в один баланс. Выдача квоты блокирует строку счёта/бюджета либо использует условный атомарный UPDATE с проверкой доступной суммы; idempotency key записывается той же транзакцией. Конкурирующая транзакция либо получает остаток после предыдущей, либо повторяет операцию с тем же ключом после конфликта.

Для ledger используем неизменяемые проводки с парой дебет/кредит; исправления оформляем компенсирующей проводкой со ссылкой на исходную. В одной транзакции Finance обновляет проводки, settlement, обязательство grant и inbox. Уникальны ID команды, ID события, `reservation_id` и расчётный бизнес-ключ `(partner_id, auction_id, imp_id)`. Это разные защиты: новый event ID не должен обходить запрет второго списания за тот же показ.

Campaign использует optimistic locking: команда несёт ожидаемую версию, обновление увеличивает её и создаёт outbox. Конфликт даёт 409, а не потерю более свежего изменения. Внешние ссылки между сервисами проверяются через контракт владельца; межсервисных SQL foreign keys после выделения нет.

## Транзакции и согласованность

| Операция | Гарантия |
| --- | --- |
| Изменить кампанию | Атомарны новые настройки и outbox; после записи кабинет читает primary либо ответ команды |
| Обновить Bidding | Eventual consistency, цель P95 ≤ 5 с, предельная свежесть 30 с; старая версия не заменяет новую |
| Выдать grant / списать расход | Локальная транзакция Finance и ограничения уникальности; решение о деньгах не читается с отстающей реплики |
| Принять событие | Collector подтверждает только Kafka ack; возможны дубликаты |
| Обновить отчёт | Eventual consistency, цель свежести P95 ≤ 60 с; UI показывает watermark и незавершённые периоды |

Между Campaign и Finance нет распределённой транзакции. Активация проходит состояния `pending_funding → active` после подтверждения Finance; отказ оставляет кампанию неактивной. Повторный запрос использует прежний ключ. Остановка исключает новые ставки после доставки статуса, но уже принятые обязательства сохраняются до расчёта.

Бизнес-правило остаётся тем же, что в Task2: `settled_spend + outstanding_grant_liability <= funded_budget`. Если сумма не сходится после восстановления, выдача новых квот останавливается. Отчёт ClickHouse и кеш бюджета в кабинете не могут разрешить дополнительный расход.

## Перенос данных из монолита

1. Назначаем владельцев таблиц, вводим роли и интерфейсы. Добавляем версии, inbox и outbox до отделения процессов.
2. Снимаем согласованный снимок домена и переносим его в новую БД, пока старый модуль остаётся единственным писателем. Догоняем изменения через outbox/журнал миграции.
3. Сверяем число записей, версии, контрольные суммы, а для Finance — счета, незакрытые grants и баланс проводок. Проверяем копию в режиме чтения.
4. На короткое окно запрещаем команды домена, дожидаемся завершения транзакций и догоняем последние изменения. Переключаем API на нового владельца и отзываем права записи старого.
5. Сохраняем старую БД только для сверки. Откат после новых записей требует обратного переноса и повторной сверки; простое возвращение маршрута создало бы две расходящиеся истории.

События продолжают поступать в Kafka во время переноса Finance. Повторы после переключения обрабатываются перенесённым inbox и бизнес-ключами, поэтому идемпотентность не начинается с нуля.

## Почему не другие хранилища

Документная БД не даёт этому проекту достаточного выигрыша, чтобы менять транзакционную модель Campaign и Finance. Один PostgreSQL для всех событий и отчётов сохраняет исходную конкуренцию нагрузки. Redis удобен для кеша, но его асинхронная репликация допускает потерю подтверждённых изменений при failover; даже `WAIT` не превращает его в строго согласованный финансовый журнал. Это ограничение описано в [документации Redis](https://redis.io/docs/latest/operate/oss_and_stack/management/replication/).

Кабинету нужны индексы PostgreSQL, Finance — его транзакции. Kafka хранит поток событий, ClickHouse обслуживает отчёты. Для описанных запросов достаточно четырёх технологий, выбранных в Task1.
