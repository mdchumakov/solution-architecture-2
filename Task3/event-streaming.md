# Потоковая обработка событий

## Поток и владельцы

Collector принимает показы, клики и уведомления партнёра, проверяет контракт и записывает их в Kafka. Finance и Analytics читают независимо. Campaign публикует изменения через transactional outbox; каждый экземпляр Bidding обновляет свою модель. Это продолжение [ADR-003](../Task1/adr/ADR-003-event-streaming.md) и [протокола событий Task2](../Task2/interaction.md#события-и-kafka).

Брокеры, controllers, consumers и диски получают отдельные лимиты ресурсов от RTB-процессов. Внутри региона начальная топология — три брокера и кворум из трёх KRaft controllers в доступных доменах отказа. Совмещение ролей в малом кластере допускается только после проверки отказа узла и IO; число VM и управляемый вариант зависят от бюджета. Три процесса на одном физическом хосте не дают независимых копий.

Начальные настройки: RF=3, `min.insync.replicas=2`, producer `acks=all`, `enable.idempotence=true`, запрет unclean leader election. Потеря одного брокера должна сохранять возможность записи; при одной доступной копии Collector не подтверждает приём. Настройки ISR и retention опираются на [документацию Kafka](https://kafka.apache.org/41/configuration/topic-configs/), но их достаточность зависит от размещения и испытаний дисков/сети.

## Topics и хранение

Сроки ниже являются начальной эксплуатационной политикой. Условие не задаёт юридических сроков финансового хранения; их нужно согласовать отдельно до удаления архива.

| Topic | Владелец / ключ | Группы потребителей | Retention и cleanup |
| --- | --- | --- | --- |
| `rtb.impressions.v1` | Collector / `campaign_id` | `analytics-events-v1`, `event-archive-v1` | 7 суток, delete |
| `rtb.clicks.v1` | Collector / `campaign_id` | Те же; отдельная группа антифрода при появлении | 7 суток, delete |
| `rtb.wins.v1` | Collector / `reservation_id` | Analytics, сверка, архив | 7 суток, delete |
| `rtb.billing.v1` | Collector / `grant_id` | `finance-settlement-v1`, `analytics-events-v1`, `event-archive-v1` | 7 суток, delete; долговечный архив обязателен |
| `campaign.changed.v1` | Campaign / `campaign_id` | `bidding-projection-{region}-{instance_epoch}`, worker кеша | 7 суток, delete; источник состояния — Campaign DB |
| `campaign.watermark.v1` | Campaign relay / ID партиции | Те же проекции | 7 суток, delete; generation и подтверждённый срез изменений |
| `finance.settled.v1` | Finance outbox / `settlement_id` | `analytics-finance-v1`, сверка, архив | 7 суток, delete; источник проводок — Finance DB |
| `rtb.quarantine.v1` | Обработчик ошибки / исходный `event_id` | `event-repair-v1` | 30 суток, delete только при наличии архива нерешённых случаев |

Дополнительные `campaign.watermark.v1` и `finance.settled.v1` уточняют heartbeat и результат расчёта из Task2; существующие topics и поля сохраняются. `campaign.changed.v1` хранит историю с delete, а не compact: для прогрева достаточно снимка и окна replay. Если позже понадобится compacted topic текущего состояния, для него отдельно определим срок хранения tombstone и правила восстановления удалённых кампаний.

Фоновый процесс архивации переносит входные события в закрытые объекты с checksum и manifest диапазонов `(topic, partition, offset)`. Начальная политика: сырые события 30 суток в рабочем архиве, billing/win, результаты расчётов и нерешённые ошибки — 90 суток без автоматического удаления до согласования сроков. Kafka с 7 сутками не является единственной копией финансовой истории.

ACL разрешает Collector писать только его входные topics, Campaign/Finance relay — только доменные изменения. Consumers имеют только чтение нужных topics и управление своей группой. Consumer финансов не получает права на изменение кампаний. TLS, служебная аутентификация и шифрование архивов защищают данные; необязательные пользовательские признаки в события не копируются.

## Схема: JSON + JSON Schema

На первом этапе выбираем JSON с версионированными JSON Schema в репозитории контрактов. Он соответствует REST/Go-адаптерам Task2 и проще для диагностики небольшой командой. Schemas проверяются producer перед публикацией и consumer до применения. Avro экономит объём и удобен при большом числе контрактов, но потребует registry и миграции клиентов; вводить его одновременно с первой Kafka-интеграцией пока не оправдано.

Пример конверта billing-события; токен сокращён и не является действующей подписью:

```json
{
  "event_id": "partner-a:billing:auction-734:imp-1",
  "event_type": "billing",
  "schema_version": 1,
  "occurred_at": "2026-10-05T08:00:00Z",
  "received_at": "2026-10-05T08:00:01Z",
  "partner_id": "partner-a",
  "campaign_id": "campaign-42",
  "auction_id": "auction-734",
  "imp_id": "imp-1",
  "trace_id": "2cf240633eb344818e51bbd0d930a270",
  "payload": {
    "grant_id": "grant-108",
    "reservation_id": "reserve-922",
    "partner_settlement_id": "settlement-550",
    "amount_micros": 1200,
    "currency": "USD",
    "reservation_token": "signed-token-placeholder"
  }
}
```

| Часть схемы | Ограничения |
| --- | --- |
| Общие поля | Непустые строки ID с ограниченной длиной, `event_type` из известного enum, `schema_version` целое положительное |
| Время | UTC в RFC 3339; `occurred_at` неизменно для одного события. Невозможное время/выход за согласованное окно отправляется в карантин |
| Деньги | `amount_micros` — целое в диапазоне int64, неотрицательное; валюта должна совпадать с grant. Клиенты не преобразуют сумму через float |
| Billing payload | Обязательны grant, reservation, токен, цена, валюта и ID расчёта партнёра; Collector проверяет подпись, Finance — обязательство и бизнес-уникальность |
| Изменение Campaign | `campaign_version`, новое состояние либо deletion marker; из Kafka нельзя сделать финансовую команду под видом настройки |
| Расширение | Новые поля необязательны; удаление, переименование, изменение единиц или бизнес-смысла требует новой версии и периода совместимости |

В примере цена — стоимость одного оплачиваемого показа в микродолях, а не внешняя CPM-цена. Она нормализуется по профилю партнёра до публикации. Контрактные тесты проверяют оба преобразования и округление резерва.

ID назначается один раз у источника или детерминированно по согласованному бизнес-ключу. Для нескольких настоящих кликов нужны разные ID; `campaign_id` или пара auction/imp недостаточны для уникальности клика. Если тот же ID приходит с другим payload, фиксируем конфликт и не выбираем произвольно «последнюю версию».

## Обработка и повторы

Collector возвращает HTTP 204 после Kafka ack. Источник повторяет неполучившее подтверждение событие; потерянный HTTP-ответ может привести к дублю. Идемпотентный Kafka producer уменьшает дубли транспортных повторов одной producer-сессии, но не заменяет устойчивый бизнес-ID при повторном HTTP-запросе.

Finance хранит inbox и проводку одной транзакцией и подтверждает offset после commit. Уникальный settlement защищает от повторного расхода и после удаления старого transport inbox. Начальный inbox TTL — 30 суток при Kafka retention 7 суток; после этого replay денег всё равно проходит через сохраняемые бизнес-ключи ledger/settlement. Их нельзя удалять, пока возможен повтор из архива или партнёрский расчёт.

Analytics вставляет события пакетами и подтверждает offset только после успешного quorum insert. После потерянного ack повтор допускается; отчёт читает канонический дедуплицированный набор по правилам [scaling.md](scaling.md#analytics-и-read-replicas). Результаты Finance хранятся отдельно от исходных billing: расходы считаются по подтверждённым settlement, а не суммой двух потоков. Несовпадение исходного требования и проведённой суммы видно в сверке.

Временная ошибка приостанавливает партицию с backoff. Невалидная схема или конфликт payload записываются в карантин с исходным topic/offset, причиной и версией обработчика; offset двигается только после надёжного сохранения карантина. Финансовое обязательство остаётся нерешённым. Исправление проходит через контролируемый replay с исходным event ID либо явно согласованную correction-команду.

При replay большой истории используем новую группу и отдельные таблицы/версию проекций. Ограничиваем чтение, чтобы не вытеснить текущий трафик, сверяем количества, контрольные суммы и суммы по кампаниям/валютам. Читающий alias отчёта переключается после сверки. Боевой финансовый consumer нельзя просто запустить с пустым inbox: replay обязан использовать существующие ключи settlement.

## Снимок и поток изменений

Чтобы прогрев не пропустил изменение на границе снимка, Legacy Adapter выполняет следующий протокол:

1. Запоминает начальные offsets C всех партиций `campaign.changed.v1` до начала SQL-снимка.
2. Открывает согласованный PostgreSQL snapshot и выгружает версии кампаний. Параллельные команды по-прежнему пишут изменения и outbox одной транзакцией.
3. Публикует manifest снимка с offsets C, checksum chunks и generation. Consumer загружает снимок и затем перечитывает поток от C.
4. Изменения, уже попавшие в снимок, отсеиваются по версии. Всё, что произошло после снимка, поступает из outbox, включая задержанные публикации. События до C уже учтены снимком, потому что публикация outbox происходит только после commit.
5. Relay выдаёт watermark только после публикации всех outbox-записей согласованного среза. Срез должен учитывать порядок commit: обычный `MAX(sequence_id)` не доказывает отсутствие ещё не завершившейся транзакции. Реализация использует барьер завершённых транзакций/commit position и вектор offsets.

Readiness требует догнать watermark и подтвердить свежесть. При разрыве истории, смене несовместимой схемы или отсутствии offsets C строится новый снимок. Для одного campaign relay сохраняет порядок версий; при нескольких workers владелец партиции/ключа один. Глобального порядка между кампаниями не требуется.

## Контроль ёмкости и задержки

Для каждой группы измеряем lag в сообщениях и секундах, скорость обработки, возраст самого старого необработанного события, время до исчерпания retention, размер ISR и свободное место. Отдельно контролируем лаг архива: финансовый topic нельзя очищать, полагаясь на ещё не завершённую архивацию.

Начальные предупреждения: проекция Campaign отстаёт более чем на 5 с, отчёт — более чем на 60 с, архив не продвигается 5 минут, до удаления непрочитанных данных меньше 24 часов. Если lag продолжает расти, увеличиваем обработку/retention в пределах диска либо ограничиваем приём нагрузки. Приём ограничиваем до подтверждения; уже подтверждённые финансовые события сохраняем.

Порядок ключей из Task2 сохраняем при первом запуске. Горячая кампания может упереться в одну партицию показов/кликов. Если тест это подтвердит, новая версия topic использует `(campaign_id, stable_bucket(event_id))`, а агрегатор объединяет бакеты. При смене числа партиций или partitioner отдельно переносим поток и проверяем порядок событий.
