# Кеширование и прогрев

## Что хранить

Bidding читает RAM-проекцию, которую фоновый worker обновляет из Campaign. Redis расположен в том же регионе в служебной сети и принадлежит Bidding. Доступ к нему не входит в критический путь ставки; потеря Redis замедляет прогрев, но не заставляет каждый bid обращаться в PostgreSQL.

| Данные | Где и срок хранения | Инвалидация / ограничение |
| --- | --- | --- |
| Кампании, таргетинг, статусы, потолок CPM | RAM до замены версии; разрешение участвовать действует не дольше 30 с без подтверждённого watermark | `campaign.changed.v1`, сравнение версий; остановка исключает кандидата после применения события |
| Снимок кампаний для прогрева | Redis `snapshot:{id}:chunk:{n}`, TTL 10 минут ±20%; manifest содержит checkpoint, хеши и версии | Новый снимок публикуется целиком до переключения указателя; TTL хранения не даёт права использовать старые данные для ставок |
| Креативы: ID, размеры, одобренный шаблон/URL | RAM/Redis в версии проекции, кеш Redis до 10 минут | Смена версии или запрет креатива исключает его; бинарные материалы остаются у Delivery |
| Базовая ставка кампании | В той же проекции, срок свежести 30 с | Меняется с версией Campaign; динамические оценки не кешируются между несвязанными аукционами |
| Повтор запроса ставки | RAM `DecisionCache`, 120 с, ограниченный объём | Тот же аукцион и digest получает тот же ответ и резерв; другой digest отклоняется |
| Остаток выданной квоты | Только RAM конкретной `instance_epoch`, до `bid_until` | Атомарные локальные резервы; после crash старая квота не переиспользуется |
| Баланс для кабинета | Необязательный кеш read API Finance на 5 с с отметкой времени | Инвалидация после проводки; платёж, grant и проверка расхода всегда выполняются в Finance PostgreSQL |
| Отчёт Analytics | Необязательный отдельный кеш API на 30 с | Ключ включает параметры и watermark; удаление/замена после пересчёта периода |

Последние два кеша не разделяют Redis Bidding: истечение массового отчёта не должно вытеснить кампании. На первом этапе достаточно кеша внутри API или вообще без кеша, пока измерения не покажут пользу.

TTL разделён на время хранения и разрешённый возраст данных. Redis может хранить снимок 10 минут для ускорения загрузки, но Bidding обязан догнать изменения и подтвердить свежесть до приёма трафика. Просроченный снимок не становится свежим оттого, что его только что прочитали из Redis.

## Инвалидация и защита от старой версии

Campaign одной транзакцией пишет новую версию и outbox. Получив событие, worker Bidding сравнивает `campaign_version`: меньшую версию игнорирует, равную с тем же содержимым считает дублем, равную с другим содержимым отправляет на сверку. Необъяснимый разрыв версии запускает обновление этой кампании/снимка. Удаление представлено событием с версией и признаком удаления, поэтому старый снимок не может вернуть удалённую кампанию.

Redis хранит неизменяемые версии объектов. Указатель на актуальный снимок меняется атомарно после записи и проверки всех chunks. Два обновляющих worker не могут заменить manifest меньшей версией: применяется сравнение generation/checkpoint в атомарной операции. Для составного checkpoint по партициям используется согласованная generation снимка, а не произвольное сравнение двух offset.

Heartbeat подтверждает состояние источника вместе с watermark. Проекция продлевает срок свежести только если применила события до этого watermark. Если обновления застряли, продолжающийся heartbeat не разрешает торговать по старым настройкам. Цель доставки — P95 ≤ 5 с; при возрасте больше 30 с кандидат исключается.

TTL кеша решений не равен TTL денег. Даже после удаления записи DecisionCache grant остаётся обеспечением обязательств до расчёта и сверки. При исчерпании памяти кеша в пределах 120 с ограничиваем новые запросы; вытеснение ещё действующей записи не должно незаметно нарушать обещание вернуть прежний результат.

## Прогрев

1. Новый Bidding получает новую эпоху, ключи проверки и доступ к своему набору данных. Пока readiness=false, bid-запросы к нему не идут.
2. Worker читает manifest Redis и проверяет chunks, контрольные суммы и версию схемы. При cache miss запрашивает снимок Campaign по фоновому API, с ограниченной конкуррентностью.
3. Применяет изменения Kafka с checkpoint снимка. Для каждого экземпляра Bidding нужна собственная группа потребления, поскольку все экземпляры должны видеть полную модель.
4. Проверяет watermark и возраст данных, строит индексы и атомарно заменяет указатель на модель. Отдельно получает новую квоту Finance; старый grant из прежней эпохи не загружается.
5. Readiness разрешается после прогрева модели и ключей. Отсутствие денег у одной кампании даёт no-bid для неё, а не отключает весь процесс.

Снимок и поток стыкуются по правилам [event-streaming.md](event-streaming.md#снимок-и-поток-изменений). Если offsets уже удалены или схема несовместима, прогрев начинается с нового снимка. Кеш не считается источником для восстановления исходных бизнес-данных.

## Пики и отказ Redis

В регионе размещаем primary и replica Redis, а для выбора нового primary — три Sentinel в разных доступных доменах отказа. Управляемая услуга допустима с эквивалентными гарантиями. AOF/RDB могут ускорить запуск, но корректность зависит от версии и повторной загрузки, а не от сохранности последнего кешированного значения. Неполный или устаревший кеш после failover отбрасывается. При росте объёма переходим на Redis Cluster по критериям [scaling.md](scaling.md#партиции-и-шарды).

Прогрев ограничен отдельным пулом: начальная настройка — не более двух одновременных загрузок полного снимка на регион, остальные ждут вне readiness. Запросы одного снимка объединяются; TTL имеет jitter, повторные попытки — backoff. Во время массового рестарта новые реплики запускаются партиями, не одновременно.

При отказе Redis прогретые Bidding продолжают работать по RAM и обновлениям Kafka. Новые процессы используют API Campaign в пределах лимита; если и он недоступен, они остаются непрогретыми. Cache miss никогда не порождает синхронный SQL-запрос из Bid.

Для Redis задаём `maxmemory`, резерв на репликацию и eviction только восстановимых ключей. Eviction незавершённого снимка допустим: отсутствие chunk делает manifest непригодным и ведёт к повторному прогреву. Для памяти Bidding отдельно считаем размер активной и строящейся модели, индексов и DecisionCache; при нехватке памяти экземпляр перестаёт принимать новые запросы до OOM.

## Контроль

Следим за возрастом модели, lag относительно watermark, долей cache miss при прогреве, временем загрузки, памятью, eviction и Redis failover. Один cache hit rate не показывает, можно ли выдавать ставку. Bidding проверяет срок последней подтверждённой модели. Проверки включают потерянное событие, старую версию после новой, удаление кампании, неполный snapshot и рестарт с потерянной квотой.
