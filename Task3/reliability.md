# Отказоустойчивость и восстановление

## Модель отказов

RPO показывает, какую часть подтверждённых данных можно потерять, RTO — время восстановления полезной работы. Время запуска процесса не показывает ни RPO, ни RTO. Сервис с поднятой БД, но непроверенными деньгами или пустой проекцией, ещё не восстановлен.

В первые три месяца защищаемся от отказа одного процесса, диска или узла внутри production-кластера. Реплики должны находиться в разных доступных доменах отказа; если таких доменов нет, заявленную защиту от потери зоны реализовать нельзя. Полная потеря кластера требует восстановления из вынесенных копий. Второй рабочий регион появляется к году.

## Цели RPO/RTO

Все значения — цели для учений на реальном объёме. Отсчёт RTO начинается с обнаружения отказа; он включает изоляцию старого владельца, восстановление, прогрев и проверку данных.

| Сервис | Отказ одного узла: RPO / RTO | Полная потеря кластера на трёхмесячном этапе | Потеря региона к году |
| --- | --- | --- | --- |
| Bidding | Нет потери исходных бизнес-данных; RAM теряется / ≤ 2 мин на замену экземпляра при живых источниках | ≤ 4 ч вместе с источниками; свежесть проверяется заново | ≤ 5 мин для переключения на готовый регион, только с его собственными квотами и свежей моделью |
| Campaign | 0 для подтверждённых sync commits / ≤ 5 мин | Цель RPO ≤ 5 мин по внешнему WAL-архиву; RTO ≤ 4 ч | Цель RPO ≤ 5 с по async WAL; RTO ≤ 15 мин после fencing и проверки среза |
| Статистика / Collector + Kafka | 0 для подтверждённых событий при потере одной из трёх копий / ≤ 2 мин | Цель RPO ≤ 5 мин по архиву; RTO ≤ 4 ч с replay; недоставленные источником события в эту гарантию не входят | Цель RPO ≤ 5 с по межрегиональному потоку; RTO ≤ 15 мин с проверкой недошедшего диапазона |
| Analytics | 0 для quorum insert; проекция может отставать / ≤ 15 мин на переключение чтения | Проекция восстанавливается до сохранённого исходного журнала; RTO ≤ 8 ч | Цель RPO ≤ 5 мин для локальной проекции, ≤ 60 мин для свежих отчётов при доступном исходном журнале |
| Finance | 0 для подтверждённых sync commits / ≤ 5 мин с проверкой grant/inbox | БД: цель RPO ≤ 5 мин; RTO ≤ 4 ч для чтения, ≤ 8 ч для записи при полной сверке | БД: цель RPO ≤ 5 с; RTO ≤ 15 мин для чтения, ≤ 60 мин для записи при полной сверке |

Для Bidding RPO=0 относится к источникам, а не к сохранению RAM. Потерянная квота остаётся заблокированной в Finance, поэтому экономический эффект сбоя — временно недоступный бюджет. Redis может быть полностью потерян: его целевой RTO ≤ 10 мин для сервиса кеша, полное наполнение ограничено временем прогрева Campaign; прогретый Bidding его не ждёт.

Асинхронные RPO ≤ 5 с/5 мин — целевой максимальный лаг, а не гарантия при любом сетевом разделении. Контролируем его и объявляем нарушение цели при превышении. Для денег потеря записей grant опаснее обычного отставания отчёта: на устаревшем балансе нельзя снова выдать уже обещанные деньги.

Поэтому Finance после региональной потери запрещает новые grants и списания до восстановления полной истории обязательств из WAL, исходных событий, архива, копий токенов и отчётов партнёра. Если полноту доказать нельзя, неизвестная часть бюджета остаётся заблокированной; целевой RTO записи может быть превышен. Если уничтожены все копии последних обязательств, восстановить их по этой схеме не получится. Если бизнес требует такой RPO при потере региона, нужен отдельно согласованный синхронный межрегиональный финансовый журнал и его стоимость/задержка.

99,9% из условия — годовая цель доступности, а не свойство каждого восстановления. Суммарные отказы измеряются за месяц; единичный долгий DR уже может исчерпать месячный бюджет. До принятия регионального финансового риска считать выполнение этого SLA доказанным нельзя.

## Резервные копии

| Данные | Политика | Восстановление и проверка |
| --- | --- | --- |
| Campaign/Finance PostgreSQL | Ежедневный base backup, непрерывная архивация WAL, 35 суток PITR; отдельные роли и ключи для копий | Восстановление в изолированную среду на выбранное время, проверка непрерывности WAL, версии схемы и контрольных сумм |
| Kafka | RF=3 для доступности; архив событий с manifest/checksum и lag ≤ 5 мин; отдельная копия конфигурации topics/ACL/schema | Развернуть журнал, восстановить события с исходными ID; offsets новых topics сопоставить через manifest, не копировать числа вслепую |
| ClickHouse | Ежедневная согласованная резервная копия таблиц и схем, хранение 14 суток; конфигурация Keeper и кластера отдельно | Восстановить факты/справочники, догнать Kafka/архив, пересчитать агрегаты; копия отдельных директорий работающего сервера не считается backup |
| Redis | Необязательные RDB/AOF для ускорения запуска; не используются для возврата grant | Полный сброс кеша и повторный прогрев — обязательный тест |
| Креативы и архивы объектов | Версионирование, контрольные суммы, отдельная копия вне production-кластера; срок бизнес-данных согласуется с владельцем | Сверить manifest и ссылки Campaign/Delivery, проверить доступность ключей дешифрования |
| Ключи проверки, конфигурация, схемы | Отдельно защищённые копии и версии; ключи старых токенов хранятся всё окно расчётов и сверки | Восстановить доступ до обработки replay; содержимое секретов не включать в Git и логи |

Копии размещаются вне отказной области production, с отдельной учётной записью и запретом обычным сервисам их удалять. Шифрование требует сохранности ключей: зашифрованный объект без доступного ключа не восстанавливает данные. Immutable/versioned хранение защищает от случайного удаления; регулярный restore проверяет, что копия пригодна.

PITR PostgreSQL требует базовой копии и непрерывной цепочки WAL; `pg_dump` полезен для логического переноса, но один ежедневный dump не выполняет RPO ≤ 5 мин. Механизм описан в [руководстве PostgreSQL по continuous archiving](https://www.postgresql.org/docs/18/continuous-archiving.html). Для короткого RPO отслеживаем фактический lag архива и принудительное завершение WAL-сегментов по таймеру, а не только время последнего запуска backup job.

## Порядок восстановления

1. Остановить маршрутизацию в неисправный контур и изолировать старых писателей. Сохранить данные для расследования; зафиксировать последний подтверждённый checkpoint и момент инцидента.
2. Восстановить доступы, ключи, сетевые правила и координаторы HA. Поднять PostgreSQL на проверенном срезе, Kafka и нужные конфигурации.
3. Восстановить Campaign, затем его снимки/поток. Для Finance сверить счета, grants, settlements, inbox и ledger. После PITR заново проверить outbox: ранее опубликованные события могли оказаться новее восстановленной БД.
4. Возобновить Collector и повторную доставку источников. Сопоставить недошедшие диапазоны архива и журналы партнёра; пометить неполноту, а не считать отсутствие событий нулём.
5. Запустить Finance consumer со старой бизнес-дедупликацией, восстановить незакрытые обязательства. Старые instance epochs не получают новые grants. Новые квоты разрешить только после проверки бюджетного инварианта.
6. Прогреть Bidding по свежей модели и новой эпохе, включить ограниченный трафик. Восстановить ClickHouse, догнать поток, сверить факты и переключить отчёты.
7. Измерить длительность и фактический пробел данных, документировать расхождения и убрать временные ограничения только после проверки владельцем домена.

Если восстановленная БД отстаёт от уже доставленных событий, нельзя просто продолжить публикацию старого outbox или принять новый баланс. Campaign сверяет версии/повторно выпускает снимок, Finance восстанавливает журнал и блокирует сомнительные средства. Для нового потока после такого восстановления используется явная generation; старая версия проекции не смешивается с новой.

## Применение 12 факторов

[12-factor](https://12factor.net/) описывает устройство приложений. Он не заменяет репликацию и резервное копирование СУБД; ниже указано, как его принципы применяются к сервисам AdScale.

| Фактор | Применение |
| --- | --- |
| Codebase | Версионируемые исходники каждого сервиса/модуля и конфигурация развёртывания, прослеживаемый commit каждого релиза |
| Dependencies | Зафиксированные версии библиотек и runtime, воспроизводимый образ, без зависимости от случайных пакетов узла |
| Config | Endpoint, лимиты и секреты передаются при запуске через окружение/секрет-хранилище, не зашиваются в код |
| Backing services | PostgreSQL, Redis, Kafka и объектное хранилище подключаются по конфигурации; смена endpoint не требует изменения алгоритма |
| Build, release, run | Один проверенный образ, отдельная версия конфигурации релиза, миграции совместимы со старой и новой версиями |
| Processes | HTTP/RPC workers не держат уникальные бизнес-данные на локальном диске; RAM Bidding восстановима, grant привязан к эпохе и надёжно учтён Finance |
| Port binding | Сервис сам публикует свой HTTP/gRPC endpoint, proxy подключается через явный порт |
| Concurrency | RTB, Collector, outbox relay и consumers масштабируются отдельными типами процессов; число consumers связано с партициями |
| Disposability | Readiness после прогрева, graceful shutdown с прекращением новых ставок; offsets только после commit, неопределённые grants не возвращаются |
| Dev/prod parity | Совместимые версии СУБД и брокера, схемы и миграции; интеграционные проверки с репликацией, а не только in-memory подменами |
| Logs | Структурированный поток stdout/stderr, централизованный сбор с лимитами; токены и персональные payload не выводятся |
| Admin processes | Миграции, сверка и replay запускаются как версионируемые отдельные jobs с аудитом, ограничением доступа и идемпотентностью |

Bidding хранит временное состояние в RAM. Его безопасная остановка зависит от протокола grants; перезапуск контейнера не возвращает деньги. У БД и Kafka собственные постоянные тома и протоколы восстановления, к которым принцип временной файловой системы приложения неприменим.
