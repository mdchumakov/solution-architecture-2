# API Gateway для DSP

## Состав и ответственность

RTB Gateway состоит из Envoy на входе и Go-адаптера OpenRTB. Envoy завершает TLS, ограничивает соединения и нагрузку, направляет запросы. Адаптер проверяет профиль партнёра, нормализует OpenRTB, вычисляет deadline, вызывает Bidding по gRPC и преобразует ответ. В [Task1](../Task1/TO-BE.md) RTB Gateway обозначен как Go-компонент; здесь раскрыт его входной proxy-слой.

Envoy выбран для сетевых политик и наблюдаемости. Реализовывать TLS, управление пулами и балансировку заново в Go не требуется. Универсальный gateway с каталогом API, плагинами кабинета и общей БД конфигурации для этого пути не нужен: он увеличит объём эксплуатации в трёхмесячном проекте. Management API Gateway обслуживает кабинет отдельно.

Минимум два экземпляра Envoy и адаптера размещаются на разных узлах за отказоустойчивым L4-балансировщиком. Bidding имеет отдельный пул. Вход Collector использует тот же технологический стек, но отдельный listener/pool, лимиты и ресурсы: всплеск кликов не должен отнимать слоты аукционов. При отказе всего production-кластера RTB будет недоступен.

## Маршрутизация и доступ

| Вход | Назначение | Политика |
| --- | --- | --- |
| `/dsp/{partner_id}/openrtb2/auction` | Go-адаптер → Bidding | Только POST, профиль OpenRTB и deadline; запрет retries |
| `/events/v1/win`, `/events/v1/billing` | Event Collector | Проверенные callback, отдельный пул, ответ после Kafka |
| `/events/v1/impressions`, `/events/v1/clicks` | Event Collector | Токены Delivery, отдельные лимиты и дедупликация |
| `/internal/*`, `/metrics`, health/admin endpoints | Только служебная сеть | Снаружи не маршрутизируются |

Партнёр аутентифицируется по mTLS; сертификат сопоставляется с `partner_id` и допустимыми маршрутами. Партнёрский ID из JSON или URL не может заменить проверенную идентичность. IP allowlist используется дополнительно. Если партнёр не поддерживает mTLS, до подключения согласуется подпись запросов с временной меткой и защитой от повторов; анонимный обход не включается.

Сертификаты и доверенные ключи обновляются с периодом перекрытия. Проверка выполняется локально, без обращения к удалённому auth-сервису на каждый bid. Между Gateway и Bidding также используется mTLS. Входные `x-partner-id`, внутренние routing headers и deadline headers удаляются и назначаются заново. Trace context принимается только после проверки формата.

Для первого профиля ограничиваем тело 64 KiB и число `imp` десятью. Сжатие запроса сначала отключено; если его потребует партнёр, ограничиваются и сжатый, и распакованный объём. Таймер чтения тела входит в общий deadline. Ключи, пользовательские идентификаторы, URL с токенами и полный OpenRTB payload не попадают в обычные access logs.

## Ограничение нагрузки

Для каждого партнёра используется token bucket до вызова Bidding. Новый партнёр добавляет примерно 3 000 RPS к существующим 15 000, но это плановый профиль, а не подписанная квота. Его фактический лимит, допустимые всплески и лимиты старых клиентов фиксируются после нагрузочного теста.

Envoy поддерживает [локальный HTTP rate limit](https://www.envoyproxy.io/docs/envoy/latest/configuration/http/http_filters/local_rate_limit_filter). Локальный bucket сам по себе не ограничивает сумму по всем репликам. Поэтому каждому ingress назначается доля `R_i` и burst `B_i` из общего лимита партнёра: `sum(R_i) <= R_partner`, `sum(B_i) <= B_partner`. Автомасштабирование не копирует полный лимит на каждую новую реплику.

Начальное burst-окно — 100 мс. Квоты конфигурации имеют эпоху и срок действия; при перераспределении сначала отзывается или истекает старая доля, затем выдаётся новая. При недоступном управляющем контуре действуют только неистёкшие доли, новый ingress не получает трафик без доли. Это уменьшает пропускную способность при сбоях, зато не требует синхронного обращения к общему Redis на каждой ставке.

Дополнительно ограничиваются одновременные запросы, CPU и длина очереди на каждом адаптере и Bidding. По закону Литтла при 18 000 RPS и 50 мс в обработке средняя суммарная конкуррентность — около 900 запросов. Лимит каждого экземпляра и запас определяем нагрузочным тестом, включая потерю одного узла. Ожидание в очереди ограничено 5 мс и оставшимся deadline. При превышении лимита запрос сразу получает 429 или согласованный технический no-bid.

## Circuit Breaker

На уровне Envoy ограничиваем подключения, активные запросы и ожидающие запросы к Go-адаптерам; retry budget для маршрута Bid равен нулю. Эти [circuit breakers Envoy](https://www.envoyproxy.io/docs/envoy/latest/intro/arch_overview/upstream/circuit_breaking) защищают ресурсы upstream. Они не заменяют автомат closed/open/half-open по доле ошибок.

Адаптер ведёт отдельный breaker для каждого endpoint Bidding. Начальные параметры: окно 10 с, минимум 20 вызовов, открытие при ≥ 50% `UNAVAILABLE`, `DEADLINE_EXCEEDED` и ошибок соединения. При малом трафике порог — пять последовательных временных ошибок. Состояние open длится 5 с, затем допускается одна проба; три успешные пробы закрывают цепь. Бизнес-no-bid не считается отказом зависимости. `RESOURCE_EXHAUSTED` учитывается как перегрузка и немедленно ограничивает приём новых запросов, без повторного вызова.

Envoy дополнительно исключает неисправные адаптеры через [outlier detection](https://www.envoyproxy.io/docs/envoy/latest/intro/arch_overview/upstream/outlier). Если здоровых upstream не осталось, возвращаем контролируемый отказ. Panic-режим отключаем, чтобы Envoy не направлял трафик заведомо неисправным экземплярам. Исключение адаптера и breaker Bidding работают на разных участках, с раздельными метриками.

Breaker влияет на выбор endpoint для новых запросов. Если текущий запрос уже вызвал Bidding и получил неопределённый результат, другой endpoint не вызывается. Это предотвращает повторное создание ставки и резерва при потерянном ответе. У Gateway нет дефолтной ставки: он может только вернуть no-bid; безопасную базовую цену выбирает Bidding после проверки кампании и квоты.

## Deadline и наблюдаемость

Общий бюджет разобран в [interaction.md](interaction.md#время-одного-запроса). Envoy ограничивает время входного запроса, адаптер уменьшает его с учётом `tmax` и сети, Bidding получает gRPC deadline. Статические proxy timeouts служат верхней границей; они не должны обнулять время, уже потраченное на чтение и проверку тела. Для маршрута Bid отключаются proxy retries, клиентские retries и hedging.

| Метрика | Для чего нужна |
| --- | --- |
| `rtb_requests_total{partner,outcome,reason}` | Объём, ставки, обычный no-bid, технический no-bid, 4xx/5xx и timeout |
| `rtb_gateway_duration_seconds`, `bidding_duration_seconds` | P50/P95/P99, хвост распределения, время по участкам |
| `rtb_deadline_miss_total`, партнёрский e2e latency | Нарушение 80 мс; внутренний таймер не заменяет измерение партнёра |
| `rtb_inflight`, `queue_wait_seconds`, `rate_limited_total` | Насыщение пулов, ожидание, потеря трафика из-за лимитов |
| `breaker_state`, `upstream_ejections_total` | Открытые цепи и исключённые экземпляры |
| `model_age_seconds`, `projection_lag`, `grant_remaining_micros` | Причины технического no-bid и исчерпание обеспеченного бюджета |
| Kafka lag, ошибки producer, очередь карантина | Риск задержанных расчётов и потери окна replay |

В labels не помещаем `auction_id`, `event_id`, user ID или неограниченное множество кампаний. Детали конкретного запроса доступны в выборочных логах и трассировках по correlation ID. Ошибки семплируются с ограничением потока; телеметрия не блокирует bid-response.

В знаменатель SLI включаем весь валидный аутентифицированный трафик в пределах договорной квоты, в том числе отвергнутый по внутренней перегрузке. Ответ 204 по технической причине считаем отказом в SLI доступности. Обычный `NO_MATCH` считаем корректным результатом, но долю ставок и доход сравниваем с контрольной группой, чтобы не спрятать деградацию подбором no-bid.

Начальные сигналы для дежурного: рост технических отказов выше 1% за 5 минут, P99 внутри Gateway выше 55 мс в течение 5 минут, возраст модели выше 20 с, открытый breaker более 30 с. Эти пороги проверим на испытаниях. Алерты на SLA настроим после согласования допустимой доли ошибок. В проекте нет подтверждённого процентиля для 80 мс, поэтому обещать соблюдение SLA по этим порогам нельзя.

На время canary сравниваем новую и контрольную группы по latency, ошибкам, доле ставок и суммам резервов. Маршруты и параметры хранятся в версии конфигурации, изменения проходят проверку и постепенное применение. При откате сохраняем обработку callback уже выданных ставок и не переиспользуем их квоты.
