# Спецификация Bidding Service

## Граница сервиса

Bidding объединяет подбор кандидатов из Ad Server и расчёт Auction Engine. Существующие алгоритмы C++ переносим без изменения правил; сетевой слой и фоновую синхронизацию реализуем на Go. Это развитие [ADR-002](../Task1/adr/ADR-002-bidding-first.md).

Сервис проверяет допустимость кампании и креатива, таргетинг, минимальную цену показа, локальную квоту и deadline. Результат — ставка с токеном резерва либо no-bid с внутренней причиной. Бюджет запроса общий для всех `imp`; отдельные аукционы не получают по 30 мс каждый.

Campaign остаётся владельцем настроек кампаний, Finance — денег и проводок, Delivery — рекламных материалов. В первые три месяца Campaign и Finance работают как модули монолита за Legacy Adapter. Bidding не читает их таблицы, не списывает деньги, не формирует отчёты и не загружает креатив по сети во время расчёта. Ссылки и согласованные шаблоны выдачи входят в локальную проекцию.

## API ставки

Внутренний интерфейс — unary gRPC `adscale.bidding.v1.BiddingService/Bid`. Gateway вызывает его один раз по постоянному HTTP/2-соединению с mTLS и передаёт оставшийся deadline. Схема ниже описывает контракт; реализация protobuf в это задание не входит.

| Поле запроса | Тип и правило |
| --- | --- |
| `partner_id`, `auction_id` | Строки; партнёр берётся из проверенной идентичности, аукцион — из OpenRTB `id` |
| `request_digest` | Хеш нормализованного содержимого для обнаружения повторного ID с другими данными |
| `impressions[]` | От 1 до 10: `imp_id`, размеры баннера, `floor_cpm_micros`, валюта, ограничения площадки |
| `context` | Разрешённые признаки площадки, устройства, региона и согласий; неизвестные признаки не додумываются |
| `auction_type`, `test` | Поддерживаемый тип аукциона; тестовый запрос не создаёт денежного обязательства |
| gRPC metadata | `traceparent`, остаток времени через gRPC deadline; внешний клиент не задаёт внутренние привилегии |

| Поле ответа | Тип и правило |
| --- | --- |
| `auction_id`, `model_version` | Идентификатор запроса и использованной модели |
| `bids[]` | Не более одной ставки на `imp_id`: `bid_id`, `campaign_id`, `creative_id`, `price_cpm_micros`, `currency`, шаблон/ссылка выдачи, `reservation_token` |
| `no_bid_reason` | Если ставок нет: `NO_MATCH`, `STALE_MODEL`, `NO_QUOTA`, `DEADLINE`, `OVERLOAD`; наружу передаётся согласованный no-bid |
| `decision_id` | Идентификатор для трассировки, не основание финансового списания |

Бизнес-отказ возвращается с gRPC `OK` и пустым `bids`. Невалидный внутренний запрос — `INVALID_ARGUMENT`, исчерпанный лимит — `RESOURCE_EXHAUSTED`, недоступность — `UNAVAILABLE`, истёкшее время — `DEADLINE_EXCEEDED`. Gateway отдельно считает технические причины, даже когда внешний контракт требует HTTP 204. Bidding проверяет отмену перед дорогим этапом и перед резервом.

Если отмена пришла после резерва, неопределённый ответ не освобождает деньги автоматически: ставка могла уйти в сеть. При повторах внутри живого процесса `(partner_id, auction_id, request_digest)` возвращает тот же результат и токены. Начальное окно дедупликации — 120 с, с ограничением памяти и ёмкости. Одновременные запросы одного ID объединяются в один расчёт. Повтор ID с другим содержимым отклоняется.

Gateway использует стабильное распределение по `(partner_id, auction_id)` и не повторяет Bid. После смены экземпляра или эпохи общий кеш ответов не гарантируется. Поэтому контракт партнёра должен запрещать повторную покупку одной пары `(auction_id, imp_id)`; Finance дополнительно дедуплицирует её. Если партнёру нужны независимые покупки под одним ID, этот профиль интеграции не подходит. Даже при повторном расчёте каждый ответ получает отдельный обеспеченный резерв, а не использует старую квоту.

## Фоновые зависимости

| Интерфейс | Назначение и ограничения |
| --- | --- |
| `GET /internal/v1/campaign-snapshots?cursor=...` | Снимок Campaign с `snapshot_id`, версиями и checkpoint по партициям. Пагинация закреплена за одним снимком |
| Kafka `campaign.changed.v1` | Изменения и удаления кампаний; ключ `campaign_id`, монотонная `campaign_version` |
| Redis, собственный кеш Bidding | Ускорение прогрева модели; не источник истины и не хранилище расходуемого остатка квоты |
| `POST /internal/v1/budget-grants` | Выдача квоты через Finance API: `campaign_id`, `instance_epoch`, сумма, валюта, срок выдачи новых ставок; обязательный `Idempotency-Key` |
| `GET /internal/v1/budget-grants/{grant_id}` | Проверка результата после неопределённого исхода POST; повтор POST с тем же ключом возвращает тот же grant |
| `POST /internal/v1/budget-grants/{grant_id}/close` | Закрытие выдачи новых ставок и запрос сверки; не немедленный возврат всего остатка |

Для REST используем JSON, mTLS, версионированные схемы и ограниченные размеры страниц. Эти API не публичные. Повтор ключа с другим телом возвращает `409 Conflict`. Finance хранит ключ и результат в транзакции выдачи; при недостатке бюджета отвечает доменным отказом без автоматических повторов.

Новый Bidding сначала получает снимок, затем догоняет поток с checkpoint и атомарно публикует готовую модель. Каждому экземпляру нужна полная проекция: у него собственная consumer group для обновлений, иначе обычная общая группа распределит кампании между процессами. Если checkpoint вышел за retention или найден разрыв версий, экземпляр заново загружает снимок.

Цель доставки изменений — P95 ≤ 5 с; предельный возраст подтверждённой модели — 30 с из Task1. Heartbeat несёт применённый watermark источника. Сам факт поступления heartbeat не продлевает жизнь модели, если экземпляр отстал от изменений. При остановке кампании применяется новая версия; при недоступной синхронизации старая версия участвует не дольше 30 с. Мгновенную остановку этот контракт не обещает.

Readiness требует готовой модели и действующих служебных ключей. Отсутствие денег у одной кампании исключает только её; оно не делает весь экземпляр нездоровым. Liveness проверяет процесс, а не доступность Finance или Kafka.

## Модель данных

| Сущность | Ключевые поля | Владелец и хранение |
| --- | --- | --- |
| `CampaignProjection` | `campaign_id`, `version`, `status`, `targeting`, `max_cpm_micros`, `currency`, `creative_ids`, `source_checkpoint`, `fresh_until` | Bidding: неизменяемые снимки в RAM, восстановимый кеш Redis; исходные настройки принадлежат Campaign |
| `CreativeProjection` | `creative_id`, `version`, размеры, проверенный шаблон/URL, статус модерации | Bidding: RAM; оригинал и доставка принадлежат Delivery |
| `BudgetGrant` | `grant_id`, `campaign_id`, `instance_epoch`, `currency`, `limit_micros`, `bid_until`, `settle_until`, `status` | Finance: PostgreSQL; Bidding хранит только выделенную ему квоту |
| `LocalReservation` | `reservation_id`, `grant_id`, `auction_id`, `imp_id`, `max_cost_micros`, `bid_id`, `issued_at` | Bidding: RAM и подписанный токен в ответе; исходный grant уже надёжно записан Finance |
| `DecisionCache` | партнёр, аукцион, digest, результат, срок удаления | Bidding: ограниченный кеш RAM, не финансовый журнал |
| `Settlement` | `partner_id`, `auction_id`, `imp_id`, `reservation_id`, цена, валюта, статус | Finance: PostgreSQL, уникальные ключи расчётного факта и резерва |
| `Inbox` / `LedgerEntry` | `event_id`, хеш payload / `settlement_id`, сумма, тип проводки | Finance: общая локальная транзакция, уникальность ID и финансового эффекта |

Внутри системы цены храним в целых микродолях валюты (`int64` с проверкой переполнения). Внешнюю CPM-цену разбираем как десятичное число без промежуточного двоичного float. Для одной потенциально оплачиваемой демонстрации резервируем `ceil(price_cpm_micros / 1000)` плюс заранее ограниченную комиссию. Если комиссия или итоговая цена могут оказаться выше известного максимума, ставку не выдаём. Пример: CPM 1,20 единицы валюты — 1 200 000 микродолей за тысячу показов и резерв 1 200 за один показ без комиссии.

## Квоты и расчёты

Finance выдаёт grant транзакционно: проверяет обеспеченный остаток, увеличивает заблокированную сумму и фиксирует ключ идемпотентности. Для кампании выполняется инвариант `settled_spend + outstanding_grant_liability <= funded_budget`. В `outstanding_grant_liability` входят и неиспользованные, и ещё не рассчитанные части квот. Уменьшить бюджет ниже уже принятых обязательств нельзя.

В одном живом процессе Bidding атомарно резервирует максимум стоимости каждого ответа. Bidding не выдаёт ставку, если для её резерва не хватает остатка grant. При нескольких `imp` сумма покрывает все возможные выигрыши. Квота принадлежит одной неизменной `instance_epoch`; новая эпоха не наследует остаток предшественника, даже если Redis сохранил копию. При failover Finance БД прежний писатель должен быть отключён до возобновления выдачи квот.

Токен резерва содержит `partner_id`, `campaign_id`, `grant_id`, `instance_epoch`, `reservation_id`, `auction_id`, `imp_id`, валюту, максимум стоимости, время выдачи и `key_id`. Bidding подписывает его своим ключом; Collector и Finance проверяют подпись и привязку к grant. Закрытые ключи доступны только соответствующему процессу; проверочные ключи сохраняются на всё окно расчётов. Подпись доказывает происхождение, а корректность расходования квоты обеспечивают алгоритм резерва и проверки Finance.

Для выбранной CPM-модели основание списания — проверенный billing callback партнёра. Win notice и браузерный impression сами по себе не создают вторую проводку. Finance проверяет grant, валюту, предел цены и пару `(partner_id, auction_id, imp_id)`, затем в одной транзакции записывает inbox, settlement и проводку, уменьшает обязательство grant. Уникальность `event_id` защищает от повторной доставки; уникальность расчётной пары защищает от дубля с новым ID. Дубликат с другой ценой попадает в сверку, а не перезаписывает проводку.

Если процесс потерял RAM сразу после ответа, Finance всё ещё хранит резерв всего grant. Проверенный callback с токеном позволяет восстановить отдельное обязательство. Остаток потерянного grant остаётся заблокированным; ни тайм-аут RPC, ни истечение `bid_until` не разрешают выдать его повторно. Loss notice также не освобождает деньги без правил финальности, согласованных с партнёром.

Предлагаемое окно расчётов — 24 часа после `bid_until`, но оно должно соответствовать реальным повторам и отчётам партнёра. Возврат остатка требует окончания окна и успешной сверки полноты обязательств. Если отчёта нет, блокировка сохраняется и создаётся инцидент. Позднее уведомление после окончательной сверки проходит отдельное разбирательство; его нельзя молча проигнорировать или списать сверх бюджета. Пока партнёр не подтверждает финальность расчётов, безопасный возврат квот не доказан.

Такая схема экономит время запроса ценой заблокированных денег. Маленькие гранты уменьшают последствия crash, но увеличивают частоту фоновых запросов. Начальный размер подбираем на 1–5 с фактической активности кампании с потолком доли её остатка; пополнение начинаем до исчерпания. Размер проверяем отдельно для активных кампаний и кампаний с небольшим бюджетом.

## Резервное поведение

При недоступном Campaign используем последнюю подтверждённую модель до её срока свежести. При отказе необязательной динамической оценки допускается сохранённая базовая CPM-ставка этой же кампании, если таргетинг, статус, креатив, floor и обеспеченная квота всё ещё валидны. Дефолтная цена ограничена `max_cpm_micros`; она не восстанавливает отсутствующие права на расход.

Если данные просрочены, неизвестна валюта, закончилась квота или истёк deadline, возвращаем no-bid. Подробная таблица отказов и повторов приведена в [interaction.md](interaction.md).
