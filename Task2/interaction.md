# Взаимодействие сервисов

## Выбор протоколов

| Связь | Выбор | Обоснование |
| --- | --- | --- |
| Партнёр → RTB Gateway | OpenRTB 2.6, JSON по HTTPS с keep-alive | Внешний отраслевой контракт; поля и расширения фиксируем в профиле партнёра |
| RTB Gateway → Bidding | Unary gRPC / Protobuf, HTTP/2, mTLS | Типизированный компактный контракт и передача deadline; генерация клиентов для Go/C++. Выигрыш по задержке проверяем измерением |
| Кабинет → Campaign | REST / JSON через Management API Gateway | Удобен для CRUD, диагностики и существующего backend; этот поток не ограничен 80 мс |
| Bidding → Campaign / Finance API | REST / JSON через Legacy Adapter, только в фоне | Не требует gRPC-обвязки всего монолита; снимки и пакетные квоты допускают более длинные тайм-ауты |
| Campaign → проекции Bidding | Transactional outbox → Kafka | Изменения доставляются независимо от запросов ставок, доступны replay и версии |
| Показы, клики, расчётные уведомления | HTTPS → Event Collector → Kafka | Источники работают через HTTP; внутренний журнал сглаживает пики и обслуживает независимых потребителей |
| Kafka → Finance / Analytics | Разные consumer groups, at-least-once | Finance выполняет расчёты, Analytics строит отчёты; медленный потребитель не блокирует другого |

REST для самого Bid допустим технически, но здесь вводим один небольшой gRPC-контракт между новыми компонентами. Расчёт ставки через Kafka не выбираем: ожидание очереди, корреляция ответа и лаг потребителя усложняют ограниченный deadline. Campaign не вызывается синхронно на каждую ставку ни по REST, ни по gRPC.

gRPC требует явно задавать deadline и прекращать ненужную работу после отмены. Это поведение описано в [руководстве gRPC](https://grpc.io/docs/guides/deadlines/); конкретные бюджеты ниже выбраны для AdScale.

## Внешний профиль OpenRTB

Gateway принимает `POST /dsp/{partner_id}/openrtb2/auction`, `Content-Type: application/json`, `x-openrtb-version: 2.6`. Версия и поддерживаемые поля фиксируются в контрактных тестах. В первом запуске поддерживаем только согласованное подмножество 2.6. Предлагаемый профиль рассчитан на баннеры и CPM, как указано в [README](README.md).

Сокращённый пример запроса:

```json
{
  "id": "auction-734",
  "at": 1,
  "tmax": 80,
  "cur": ["USD"],
  "imp": [{
    "id": "imp-1",
    "banner": {"w": 300, "h": 250},
    "bidfloor": 0.8,
    "bidfloorcur": "USD"
  }],
  "site": {"id": "site-42", "domain": "publisher.example"}
}
```

Gateway проверяет обязательные ID, уникальность `imp.id`, размеры, валюту, тип аукциона и ограничения партнёра. Неподдерживаемый формат даёт no-bid для соответствующего `imp`; некорректный JSON или нарушенная схема запроса дают 400. Неизвестные необязательные поля допускаются, известные ограничения безопасности и приватности сохраняются при нормализации.

Успешный ответ содержит тот же `id`, `seatbid[].bid[].id`, `impid`, `price`, `crid`, `adomain`, согласованную выдачу через `adm` и валюту `cur`. Цена `price` выражена в CPM. Gateway формирует `nurl` и `burl` с подписанным токеном резерва; расчётная цена приходит отдельно в согласованном macro/поле и проверяется по пределу резерва. Имена endpoint и способ аутентификации ниже — наш профиль, а не обязательные поля стандарта.

| HTTP-ответ на запрос ставки | Значение |
| --- | --- |
| `200` + BidResponse | Найдена хотя бы одна обеспеченная ставка |
| `204`, пустое тело | Валидный запрос без ставки; причина остаётся в метриках |
| `400`, пустое тело | Некорректный запрос |
| `401/403`, `413`, `429` | Ошибка доступа, слишком большой запрос, превышение согласованного лимита |
| `503` | Сервис недоступен; если партнёр требует 204 вместо 503, адаптер меняет ответ, но сохраняет техническую ошибку в SLI |

Транспорт, коды 200/204/400, `tmax`, CPM-цена и различия уведомлений определены в [OpenRTB 2.6](https://github.com/InteractiveAdvertisingBureau/openrtb2.x/blob/main/2.6.md). `nurl` сообщает о выигрыше и не доказывает, что показ стал оплачиваемым; `burl` относится к расчётному событию по правилам площадки. Поэтому для этой интеграции списание связано с подтверждённым billing callback, а win и браузерный impression используются отдельно.

## Время одного запроса

| Участок | Проектный бюджет |
| --- | --- |
| Сеть между партнёром и AdScale в обе стороны | 20 мс |
| Вход Gateway: TLS на постоянном соединении, проверка и нормализация | 5 мс |
| Внутренняя передача и ограниченная очередь | 5 мс |
| Подбор кандидатов, расчёт всех `imp`, локальный резерв | 30 мс |
| Сериализация и возврат через Gateway | 5 мс |
| Внутренний резерв | 15 мс |
| Всего | 80 мс |

Таблица распределяет время одного запроса. Складывать измеренные P95 отдельных этапов для проверки SLA нельзя. Отсчёт на Gateway начинается при первых байтах запроса, включая чтение тела. Локальный предел ответа: `D = min(80 мс, tmax либо 80 мс) - 20 мс`. Если `D <= 0` или времени на полезный расчёт не осталось, Gateway не вызывает Bidding.

Gateway передаёт Bidding остаток до `D - 5 мс`, чтобы оставить время на ответ. Из исходных 60 мс внутри AdScale это обычно не более 50 мс после входной проверки; вычислительная цель Bidding — 30 мс. Каждый этап использует монотонные часы и вычитает потраченное время из общего остатка. При исчерпании времени Gateway отменяет RPC и возвращает no-bid до локального предела. Если соединение уже оборвано, результат учитывается как технический отказ.

Резерв 20 мс не гарантирует реальную сеть. Партнёрский замер и синтетический probe должны подтвердить его достаточность; при большем RTT уменьшаем бюджет вычисления или меняем размещение. Допустимую долю превышений согласуем до запуска.

## События и Kafka

Collector принимает `GET /events/v1/win` и `GET /events/v1/billing` по callback URL с токеном, а также `POST /events/v1/impressions` и `POST /events/v1/clicks`. Поддержка GET/POST конкретным партнёром закрепляется отдельно. Для server-to-server уведомлений проверяется идентичность партнёра и подпись/токен, для браузерных — выданный Delivery ограниченный токен. Браузерный токен не даёт права создать billing-событие.

| Topic | Ключ | Потребители |
| --- | --- | --- |
| `rtb.impressions.v1` | `campaign_id` | Analytics |
| `rtb.clicks.v1` | `campaign_id` | Analytics, антифрод при появлении |
| `rtb.wins.v1` | `reservation_id` | Analytics, сверка |
| `rtb.billing.v1` | `grant_id` | Finance, Analytics |
| `campaign.changed.v1` | `campaign_id` | Каждый экземпляр Bidding, собственная группа |
| `rtb.quarantine.v1` | ID исходного события | Разбор ошибок с причиной и ссылкой на исходный topic/offset |

Конверт события содержит `event_id`, `event_type`, `schema_version`, `occurred_at`, `received_at`, `partner_id`, `campaign_id`, `auction_id`, `imp_id`, `trace_id` и payload. Для billing нужны `grant_id`, `reservation_id`, токен, цена, валюта и ID расчёта партнёра. Если у источника нет event ID, Collector вычисляет устойчивый ID из согласованного бизнес-ключа; случайный UUID на каждом повторе не подходит. Для разных реальных кликов источник должен выдавать разные ID, даже если аукцион один.

Предлагаемые настройки из [ADR-003](../Task1/adr/ADR-003-event-streaming.md): RF=3, `min.insync.replicas=2`, producer `acks=all` и `enable.idempotence=true`, запрет unclean leader election. Retention начинается с 7 суток. Схемы проверяются на совместимость: новые поля необязательны, несовместимый смысл требует новой версии контракта. Порядок гарантируется только внутри партиции; время события не равно порядку поступления.

Collector отвечает 204 только после подтверждения Kafka. Если producer исчерпал свой ограниченный timeout, Collector возвращает 503. Неопределённый результат записи допускает повтор: событие могло сохраниться, поэтому потребителям нужна дедупликация. Начальный бюджет приёма callback — 1 с, отдельно от аукционных 80 мс; его согласуем с источником.

Finance фиксирует inbox и проводку одной SQL-транзакцией, затем подтверждает offset. Crash между commit и offset даёт повтор без нового списания. Analytics хранит уникальные события и строит агрегаты по дедуплицированному набору; слепое прибавление счётчика при replay запрещено. Kafka не обеспечивает однократный эффект во внешнем PostgreSQL автоматически — это граница её [гарантий доставки](https://kafka.apache.org/41/design/design/#message-delivery-semantics).

При временной ошибке Finance приостанавливает обработку затронутой партиции с ограниченными повторами. Детерминированно ошибочное событие сначала надёжно записывается в карантин и журнал инцидентов; только потом можно продвинуть offset. Если карантин недоступен, offset не сдвигается. Такой перенос не означает успешный расчёт: обязательство остаётся заблокированным до исправления и replay.

Частота показов и кликов неизвестна. Число партиций и объём дисков выбираем по измеренным events/s, размеру события, retention и пику горячей кампании, а не напрямую по 18 000 bid RPS. При lag, приближающемся к retention, увеличиваем доступное окно хранения или восстанавливаем данные из финансового архива и отчётов партнёра. Retention не заменяет архив.

## Повторы и отказы

Для фоновых запросов используем full jitter: `delay = random(0, min(cap, base × 2^attempt))`. На каждом уровне есть один владелец повторов; вложенные retry в Gateway, клиенте и адаптере отключены.

| Операция | Политика |
| --- | --- |
| Bid | Один вызов, без retries и hedging. Новый запрос после отказа может попасть на здоровый экземпляр |
| Снимок Campaign | Timeout 2 с на страницу, до 3 попыток; base 100 мс, cap 1 с; затем фоновый resync |
| Выдача/закрытие квоты | Timeout 500 мс, до 3 попыток с тем же idempotency key; base 100 мс, cap 1 с; после неопределённого исхода запрос статуса |
| Callback источника | Предлагаем до 5 быстрых попыток, base 200 мс, cap 5 с, затем долговечная очередь партнёра и доставка в пределах окна расчётов |
| Outbox / consumer | Ограниченный пакет попыток, base 200 мс, cap 30 с; после исчерпания пауза и alert, исходная запись не удаляется |

Повторяем только временные сетевые ошибки, 429 с учётом `Retry-After` и подходящие 5xx. Ошибки схемы, прав и бизнес-отказы не повторяем автоматически. Для финансового POST повтор без устойчивого ключа запрещён. Если браузер закрылся до подтверждения Collector, сохранность такого события не гарантируется; расчёты опираются на server-to-server доставку и сверку.

| Отказ | Поведение и восстановление |
| --- | --- |
| Campaign/адаптер недоступен | Ставки по подтверждённой RAM-модели до 30 с; затем исключение устаревших кампаний, фоновый resync |
| Redis недоступен | Прогретый Bidding работает; новый экземпляр загружает снимок Campaign или остаётся вне readiness |
| Finance недоступен | Работа в пределах уже выданной квоты; после исчерпания no-bid. Circuit Breaker прекращает новые попытки до пробного вызова |
| Bidding упал после резерва | Новый процесс получает новую эпоху; старый grant блокируется до сверки; Gateway не пересчитывает тот же запрос |
| Kafka недоступна | Collector возвращает 503; outbox сохраняет изменения. Ставки ограничены свежестью модели и остатком квот |
| Finance consumer отстаёт | Растёт заблокированная сумма; Finance ограничивает выдачу новых квот по доступным средствам, без кредита под ожидаемые события |
| Analytics недоступна | Растут lag и возраст отчётов; ставки и расчёты продолжаются |
| Нет подходящей рекламы | Обычный no-bid, отдельно от технической деградации |

Circuit Breaker фоновых клиентов ведёт состояния closed/open/half-open: в окне 10 с после минимум 20 вызовов доля временных ошибок ≥ 50% открывает цепь на 5 с; один пробный запрос проверяет восстановление, три успешных пробы закрывают цепь, ошибка снова открывает. Снимки и квоты имеют отдельные breakers и пулы. При низком трафике пять последовательных временных ошибок также открывают цепь. Настройки требуют испытаний.

![От ставки до расчёта](diagrams/sequence.svg)

Sequence показывает успешную ставку и последующий billing callback. Расчёт и резерв выполняются внутри Bidding перед ответом, без внешнего RPC. Callback возникает позже и не входит в deadline 80 мс. Finance может обработать событие как до отправки HTTP-подтверждения Collector, так и после него: обязательный порядок только `Kafka ack → HTTP ack` и `SQL commit → offset`.
